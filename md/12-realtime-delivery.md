# 12 · 실시간 전송

> 확정된 상태를 구독자에게 밀어내고, 재연결과 캐시 장애에서 복구한다.
> 참조: [공통 규약](01-conventions.md) · [상태 계약](03-state-contract.md)

무엇을 보내는지는 `03`이 정한다. 이 문서는 **어떻게 보내고 어떻게 복구하는가**를 다룬다.

---

## 1. 룸

| 룸 | 무엇을 받나 |
|---|---|
| `trip:{trip_id}` | 회차 상태 변경 |
| `route:{route_id}` | 노선 단위 공지, 시간표 변경, 후보 변경 |

학생 앱은 **노선을 고르면 `route` 룸에, 회차를 고르면 `trip` 룸에** 가입한다. 회차 선택 전부터 노선 룸에 있어야 공지를 받는다.

정거장별 룸은 두지 않는다. 정거장 선택은 클라이언트가 전체 상태에서 해당 방문을 골라 표시한다. 규모가 커지면 그때 추가한다.

## 2. 이벤트

| 방향 | 이벤트 | 내용 |
|---|---|---|
| 학생→서버 | `trip:subscribe` / `trip:unsubscribe` | `trip_id`. 가입 승인 응답 |
| 학생→서버 | `route:subscribe` / `route:unsubscribe` | `route_id` |
| 서버→학생 | `trip:state` | `state_version`·`control_version`·`stops[]`·`vehicles[].visits[]` |
| 서버→학생 | `notice:changed` | `{route_id, trip_id}`. 유효 공지 재조회 |
| 서버→학생 | `schedule:changed` | `{route_id, service_date}`. 날짜 상태·후보 재조회 |
| 서버→학생 | `candidates:changed` | `{route_id, service_date, affected_trip_ids[]}`. 후보 재조회 |

**`trip:state`는 REST `/state`와 같은 구조를 보낸다** (`03` 1장). 차량 배열만 보내면 화면이 정거장 이름·순번·승하차 정책을 얻지 못한다.

### `candidates:changed` 발행 조건

후보 목록(`11` 3장)은 세 층으로 결정된다.

| 층 | 무엇 |
|---|---|
| (a) 집합 | 어떤 회차·차량이 목록에 들어가나 |
| (b) 분류 | `candidates`냐 `unverified_candidates`냐 |
| (c) 숫자 | 각 후보의 `sort_at`·예상 시각 |

**(a) 또는 (b)가 바뀔 때만 발행한다.**

| 발행함 | 발행하지 않음 |
|---|---|
| 회차·차량이 cancelled 또는 completed로 전이 | `estimated_event_at` 값만 변경 |
| 회차 신규 생성 (`05` 보충·개정), 완료 오판 재검토로 운행 재개 | `state_version`만 증가 |
| 승차 방문이 upcoming→arrived, arrived→departed·passed·passed_inferred로 전이 | 캐시 복원 |
| 승하차 정책 변경 | `schedule_status` 변경 — `schedule:changed`가 담당 |
| 후보가 두 배열 사이를 이동 (신선도 만료, position_unverified·stale_observation 진입·해제) | 같은 분류가 유지되는 상태 갱신 |

(c)는 이미 `trip:state`로 해당 회차 구독자에게 전달된다. **`candidates:changed`는 `route` 룸이므로 그 노선을 보는 모든 학생을 깨운다.** (c)로 발행하면 중복 전송이면서 노선 전체를 반복 재조회시킨다.

(b)는 입력 없이 **시간 경과만으로도** 바뀐다 (`11` 5장). 실제 주체는 08 8장의 `expire_predictions`이며, 그 배치가 분류를 바꾼 회차에 대해 발행한다.

`candidates:changed`는 선택한 route_id와 service_date가 모두 일치하면 현재 후보 목록 포함 여부와 관계없이 재조회한다. 신규 회차, 완료 오판 후 운행 재개, 승하차 정책 정정으로 지금 목록에 없는 회차도 후보가 될 수 있기 때문이다. `affected_trip_ids`는 영향 범위 참고 정보이며 조회를 생략하는 필터로 쓰지 않는다. 다른 노선·날짜의 이벤트는 무시한다. 짧은 시간에 알림이 여러 개 오면 진행 중 조회 이후 한 번의 추가 조회로 합쳐 최종 변경을 놓치지 않는다. 이벤트를 놓쳐도 refresh_after_seconds(초기 30) 폴백으로 회복한다.

`schedule:changed`와 `candidates:changed`를 같은 변경으로 함께 보내지 않는다. 재연결·날짜 변경 절차에서 화면이 이미 둘 다 재조회한다.

### 전송 범위

| 공지 범위 | 전송 룸 |
|---|---|
| 특정 회차 (`trip_id` 있음) | `trip:{trip_id}` |
| 노선 전체 (`trip_id` 없음) | `route:{route_id}` |

노선 단위 공지가 도달할 룸이 없으면 회차를 고르기 전의 학생이 공지를 못 받는다.

## 3. 동기화 절차

구독 승인과 REST 조회 사이에도 변경이 일어난다. **그 사이 변경을 놓치지 않는 순서**가 중요하다.

```
1. 이벤트 수신 핸들러를 등록하고 pendingStates 버퍼 모드를 켠다
2. trip:subscribe 를 보내고 승인을 받는다
3. 요청 전부터 REST 완료까지 도착한 해당 trip 이벤트를 모두 보관한다 (승인보다 먼저 온 이벤트 포함)
4. REST /state 를 조회한다
5. 조회 응답의 state_version 보다 큰 임시 이벤트만 순서대로 반영한다
6. 이후 이벤트는 바로 반영한다
```

**핸들러 등록이 구독보다 먼저**여야 승인 직후 이벤트를 놓치지 않는다. **임시 보관이 있어야** 조회 응답이 오는 동안의 변경이 사라지지 않는다.

### 버전 규칙

- **더 큰 `state_version`만 반영한다.** 응답과 이벤트가 역순으로 도착해도 낮은 버전으로 되돌리지 않는다.
- 버전 공백이 발견되면 다시 조회한다.
- 재연결·구독 실패 시 다시 조회한다.
- 회차 전환 시 이전 구독을 해제하고 임시 이벤트를 버린다. `trip_id`를 검증한다.

### 재연결

```
연결 복구
  → route·trip 룸 재구독
  → 날짜 자료 상태 재조회
  → 후보 목록 재조회
  → 회차 상태 재조회
  → 유효 공지 재조회
```

**저장된 화면을 실시간으로 표시하지 않는다.** 끊긴 동안의 변경을 알 수 없으므로 전부 다시 읽는다.

`schedule:changed` 수신 시에도 날짜 상태와 후보를 다시 조회한다.

### 공지 만료

`notice:changed`를 받으면 유효 공지를 다시 조회한다. **만료 시각이 되면 서버 이벤트를 기다리지 않고 배너를 제거한다.** 만료된 공지를 계속 표시하지 않는다.

## 4. 전송 보장

### Outbox

DB 저장이 성공했는데 전송이 실패하면 상태가 어긋난다. **확정과 전송을 분리한다.**

```
회차 단위 잠금
  ├ 이벤트·차량 상태·예측·state_version 확정
  └ outbox 레코드 생성        ← 같은 트랜잭션

  (커밋)

drainOutbox
  → 미전송 항목을 룸에 전송
  → 성공 시 표시
```

- 전송 실패는 재시도한다.
- **재시도로 중복될 수 있으므로 소비자는 멱등 처리한다.** 같은 버전을 두 번 받아도 문제없다.
- 전송 가능한 **완성된 상태 버전만** 내보낸다. 미완성 계산 결과를 새 버전으로 공개하지 않는다.

## 5. 캐시

Redis는 **확정된 상태의 복제본**이다. 기준 데이터가 아니다.

| 원칙 | 내용 |
|---|---|
| 기준 | PostgreSQL |
| 캐시 | Redis. 언제 사라져도 DB에서 복원 가능해야 한다 |
| 복원으로 새 이력 생성 금지 | 복원만으로 새 예측 이력을 만들지 않는다 |
| 같은 상태 복원 | **새 버전을 만들지 않는다** |

### 복원 시작 조건

| 조건 | 처리 |
|---|---|
| 서비스 시작 | 오늘 진행 중인 회차 복원 |
| Redis 재연결 후 캐시 누락 | 누락분 복원 |
| 개별 회차 캐시 누락 | 그 회차만 복원 |
| **Redis만 재시작** | 서비스 재시작 없이 복원 |

마지막 항목이 중요하다. Location 서비스를 재시작하지 않고 Redis만 초기화해도 복구돼야 한다.

### 복원 절차

```
1. 대상 선정
   시작 시 오늘 조회 대상 회차를 우선 복원
   개별 조회 시 필요한 날짜·회차의 확정 스냅샷을 복원
   완료·취소 회차도 해당 공개 상태 그대로 복원

2. DB에 확정된 동일 state_version의 상태 본문을 읽음
   방문·차량 상태·예측을 같은 확정 스냅샷으로 복사
   복원 경로에서 현재 통계로 예측을 다시 계산하지 않음

3. 버전 비교
   복원 작업의 과거 상태가 동시 입력의 새 상태를 덮지 않도록
   state_version 비교와 회차별 동시 처리 제어를 적용한다

4. 캐시 반영
```

### 복원 중 조회

두 가지 중 하나로 응답한다.

| 방식 | 응답 |
|---|---|
| DB 직접 조회 | 정상 200. 느리지만 정확 |
| 거절 | `503 CACHE_REBUILDING`, `retryable = true`, 재시도 안내 |

**Location 서비스의 Readiness가 다른 서비스까지 자동으로 차단한다고 가정하지 않는다.** 조회 경로가 자기 상태를 스스로 판단한다.

### Redis 영속성

AOF는 **별도 학습 항목**이다 (`14`). 활성화하더라도 DB 기준 상태와 버전을 확인한 뒤 사용한다. 캐시 파일을 기준 데이터로 삼지 않는다.

## 6. 서버 구성

MVP는 단일 백엔드로 시작하고 단계적으로 분리한다 (`14`).

| 구성 | 책임 |
|---|---|
| Notification Service | Socket.IO 서버, 룸 관리, outbox 소비 |
| Redis | 상태 캐시. 서비스 분리 후에는 pub/sub 채널도 |

서비스가 분리되면 **여러 인스턴스가 같은 룸의 구독자를 나눠 갖는다.** Redis 어댑터로 인스턴스 간 브로드캐스트를 연결한다.

## 7. 프론트 상태

| 변수 | 의미 |
|---|---|
| `connectionStatus` | 로컬 `connecting` / `connected` / `disconnected` |
| `stateVersion`, `controlVersion` | 마지막 반영 버전 |
| `pendingStates` | 조회 대기 중 임시 보관 이벤트 |
| `subscribedTripId`, `subscribedRouteId` | 현재 구독 |

**`connectionStatus`를 운행 상태나 정보 상태로 저장하지 않는다** (`03` 4장). 서버 연결이 끊긴 것과 버스 정보가 없는 것은 다르다.

화면은 필요할 때 ‘정보 갱신 중’으로 표시하고 마지막 상태에는 마지막 확인 시각을 남긴다. 앱의 서버 연결 지연을 차량 GPS 장애라고 표시하지 않는다. GPS 위치 재확인은 03의 ‘위치 확인 중’을 쓴다. 유효기간이 지난 ETA는 계속 표시하지 않는다.

## 8. 함수

| 함수 | 처리 |
|---|---|
| `subscribeTrip` | trip 룸 가입 후 승인 |
| `subscribeRoute` | 노선 룸 가입. 공지·시간표·후보 변경 수신 |
| `publishTripState` | 확정 버전·`stops[]`·`vehicles[].visits[]` 전송 |
| `publishNoticeChanged` | 범위에 맞는 룸으로 재조회 알림 |
| `publishScheduleChanged` | route 룸에 날짜·노선 알림 |
| `publishCandidatesChanged` | route 룸에 후보 재조회 알림. 집합·분류 변경에만 발행 |
| `drainOutbox` | 확정된 미전송 항목 재시도 |
| `commit_trip_state` | 새 상태 → DB 버전·outbox. 완성된 상태만 공개 |
| `rebuild_trip_cache` | 회차 → 확정 DB 상태 복제. 복구로 새 예측 생성 금지 |
| `syncTripState` | tripId → 스냅샷·이벤트 병합 |
| `applyTripState` | 상태 → 더 새 버전만 적용 |

## 구현 메모 (P4, 2026-09-15)

설계에 없던 부분을 구현에서 정했다. 다르면 이 절과 `app/realtime`을 함께 고친다.

| 항목 | 결정 |
|---|---|
| 구성 | MVP 단일 백엔드. Socket.IO(`python-socketio`)를 API 프로세스에 붙인다 (`uvicorn app.main:asgi`, 경로 `/socket.io`). outbox 전송·상태 만료 확정 작업도 같은 프로세스(`REALTIME_WORKERS`). 인스턴스를 늘리면 `REDIS_URL`로 Redis 매니저가 룸을 잇고 outbox는 `SKIP LOCKED`+임대 기한으로 나눈다 |
| 스냅샷 | `trip_state_snapshots`는 **회차마다 최신 한 행**. 버전별 이력은 저장 비용 때문에 두지 않는다. 과거 사실은 관측·결정 이력이 보존한다 |
| 확정 함수 | `commit_trip_state` — 회차 잠금 아래 지금 계산한 내용이 스냅샷과 다를 때만 새 버전·스냅샷·outbox를 한 트랜잭션에 넣는다. 관측 입력·취소·검토·복구·완료·취소·재검토가 모두 부른다 |
| 시간 경과 | 30초 주기(`STATE_REFRESH_SECONDS`)로 어제·오늘 회차를 다시 계산해 바뀐 것만 확정한다(`expire_predictions` 역할). `/state` 조회도 내용이 달라졌으면 그 자리에서 확정한다 |
| `candidates:changed` 판정 | 방문마다 '이 방문에서 탄다면'의 분류 결과(제외·추천·확인 필요·사유)와 하차 정책을 서명으로 저장하고, 서명이 바뀔 때만 발행한다. 예상 시각 숫자는 서명에 없다. 첫 스냅샷은 변경이 아니다 |
| 회차 추가 | 이미 회차가 있던 날짜에 회차가 더 생기면 `candidates:changed`. 처음 생성은 발행하지 않는다. 날짜 판정이 바뀐 경우 `schedule:changed`만 보낸다 (FR-RT-18) |
| 전송 | 적재 순서대로 보낸다. 실패는 30초 임대 기한 뒤 재시도. 보낸 기록은 하루 뒤 삭제 |
| 캐시 | Redis 해시 `shuttlebus:trip_state:{trip_id}`. Lua로 더 새 버전만 쓴다. 누락·장애 시 DB 스냅샷을 읽고 다시 채운다. 복원 중 503은 쓰지 않는다(항상 DB 응답, 5장 두 방식 중 첫째) |
| 구독 응답 | `{ok, trip_id}` 또는 `{ok: false, code}`(`VALIDATION_ERROR`·`RESOURCE_NOT_FOUND`). 인증 없음(학생 공개 정보) |
| 서버 시각 | `app/clock.get_now` 한 곳에서만 읽는다. 달력의 '과거 날짜 보존' 판단도 같은 시각을 쓴다 |

실측 (Docker, 2026-09-15): 공지 생성 → `notice:changed` 0.17초, 회차 취소 → `trip:state`·`candidates:changed` 0.29초 (NFR-01 2초). Redis `FLUSHALL` 뒤 `/state`가 같은 버전으로 응답하고 캐시가 다시 채워짐 (FR-RT-07·09).

## 10. 버전이 관리하는 상태와 복원

`trip_state_snapshots(trip_id, state_version, payload, committed_at)` 또는 동등한 DB 확정 상태 저장 구조를 둔다. payload와 outbox는 같은 트랜잭션에서 확정한다. 복원은 이 값을 읽는 작업이며 새 예측 이력을 만들지 않는다.

만료·새 통계 적용으로 상태가 바뀌면 정상 상태 갱신 경로에서 새 state_version으로 확정한다. DB 직접 조회도 재계산한 다른 내용을 기존 버전으로 반환하지 않는다. server_time은 응답 생성 메타데이터이므로 본문 상태 버전과 구분한다. 오래된 스냅샷의 만료 처리 실패를 ‘캐시 복원 성공’만으로 최신 정보라고 표시하지 않는다.

노선 전환 시 이전 route·trip 구독과 요청 버퍼를 정리한다. 현재는 선택한 route와 trip만 구독한다. 출발·도착 변경 시 이전 후보·선택 회차를 비우고 재조회한다. 전체 노선 페이지와 여러 노선 동시 후보 구독은 후순위다.

관측 취소로 통계가 무효화되면 08의 영향 회차 상태 갱신과 같은 트랜잭션에서 outbox를 기록한다. 통계 차단 때문에 후보 분류가 바뀌면 candidates:changed를 발행한다. 캐시 복구는 차단 전 버전을 최신으로 되살리지 않으며 현재 DB 확정 버전을 따른다.
