> CLAUDE.md 2장에 따라 단계마다 멈춘다. 8장 결정은 전부 제안대로 확정했다 (4번은 소문자 유지). 2단계에서 바뀐 파일은 5장 표에 있다.

## 1. 왜 — 할 일의 상태가 다섯 곳에 흩어져 있다

같은 할 일의 상태가 여러 문서에 따로 적혀 있다. CLAUDE.md 1장("규칙은 소유 문서 하나에만")과 어긋난다.

| 같은 할 일 | 적힌 곳 |
|---|---|
| 직접 탑승 기록 2~3회 | ROADMAP '남은 작업' 2번, IMPROVEMENTS '사용자 확인 대기' 7번, README '진행 상황' P5 |
| 미검증 마커·경로 요청 취소 | REVIEW-2026-09-21 P2, REVIEW-2026-09-22 P2, must_do F8, PLAN-screen-fixes 2·3절 |
| P6 착수 조건 | ROADMAP P6, PLAN-route-data 순서 8, IMPROVEMENTS 1순위·6번 |

관리판은 **상태(할 일·진행·검수·완료)의 소유자를 하나로** 만들고, 단계(P0~P8)별 진행도·"바로 할 수 있는 작업"·AI의 자동 등록과 진행 기록을 한 화면에 모은다.

## 2. 무엇을 넣나

바른자세(sitting-posture-corrector) 팀 관리판을 1인용으로 줄인 **프로젝트 관리판 템플릿**을 쓴다.

| 항목 | 내용 |
|---|---|
| 실행 | Python 표준 라이브러리만. `127.0.0.1` 전용, 외부 연결 없음. `api/.venv`와 무관 |
| 화면 | 한눈에 보기 · 프로젝트 여정(단계별 진행도 + md 문서 서가·읽기) · 진행 보드(5단 칸반) |
| 저장 | 카드는 `workspace.json` 한 파일. 원자 저장, 버전 충돌 거절(409), 손상 파일 비덮어쓰기, 번호 재사용 금지 |
| AI 명령 | `work.py` — add · create-doc · sync-plans · move · log · link · next · inbox · check |
| 검증 | 템플릿 시험 20개 통과, 빈 프로젝트·표본 프로젝트·휴대폰 폭 브라우저 확인(콘솔 오류 0). **클라우드 작업 공간에서 확인했고 ShuttleBus에는 아직 설치·실행하지 않았다** |

**위치: `scripts/board/`.** `tools/`는 없고, `.tools/`는 git 제외 로컬 도구 폴더라 이름이 헷갈린다. 루트 실행 파일은 `관리판.cmd`.

**`.bat`이 아니라 `.cmd`인 이유.** `.gitattributes`의 `* text=auto eol=lf`가 `.bat`을 LF로 바꿔 저장하는데, LF 배치 파일은 Windows에서 `goto` 이동이 어긋날 수 있다. `*.cmd text eol=crlf` 규칙이 이미 있어 `.cmd`는 CRLF로 유지된다 (`setup.cmd`와 같은 방식). 실행 동작은 같다.

P0 골격 · P1 기준 자료 · P2 시간표 학생 화면 · P3 수동 수집 · P4 실시간 · P5 통계·예측 · P6 GPS 자동화 · P7 화면 완성 · P8 Kubernetes, 그리고 상시 운영(문서·도구·검토, 진행률 제외).

## 3. 상태를 옮기는 방식 — A안 (카드가 상태 소유)

### 원칙

1. **md의 행·ID·설명은 지우지 않는다.** 코드 주석 19곳(api 15 · web 4)이 이 ID를 가리킨다 — `must_do S2·F2·F3·F8`, `IMPROVEMENTS 한계 1·2·4`, `REVIEW-2026-09-21 P1`, `REVIEW-2026-09-22 P1·P2`, `PLAN-route-data ②`.
2. 바뀌는 것은 **상태 문구만**이다. `**완료 (2026-09-18)**`·`대기`·취소선 같은 표시를 카드 번호(`SB-0012`)로 바꾼다. 상태 문구에 붙어 있던 설명(계약 요약·경로 등)은 설명 칸에 그대로 남긴다.
3. 카드에는 원래 ID를 `ref`로 남긴다 (예: `ref: must_do C1`). 화면·검색에서 원래 ID로 찾을 수 있다.
4. 이미 끝난 항목도 **완료 카드**로 등록한다. 근거(evidence)에는 md에 적힌 완료 날짜·검증 문구를 옮긴다. 그래야 단계 진행도가 실제와 맞는다 (8장 결정 5).
5. 완료된 단계(P0·P1·P4 등)는 단계 요약 카드 1장씩을 완료로 등록한다. 근거는 ROADMAP '끝난 것' 표와 CHANGELOG.

## 6. C안으로 바꾸는 기준

- 4번 작업에서 상태와 설명을 나누기 어려운 행이 많을 때 (대상 행의 절반 이상)
- 외부 화면 담당자가 실제로 GitHub의 must_do만 보고 작업하게 될 때 — 관리판은 로컬 도구라 그 사람에게 보이지 않는다

C안: 단계(P0~P8)와 must_do·IMPROVEMENTS의 상태 문구는 md가 그대로 소유한다. 카드는 **미완료 항목만** 등록하고 진행 기록·선행 관계·AI 기록을 맡는다. 완료 처리 때 md 문구도 함께 고친다.
