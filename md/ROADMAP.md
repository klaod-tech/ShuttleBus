# 구현 순서

> **진행 상황 (2026-09-18):** P0·P1·P2 서버·P3·P4 **완료**. P2 화면과 P7은 화면 단계에서 함께 한다.
> P5는 실측 표본이, P6은 설치 허가와 경로 자료가 있어야 시작한다. 남은 일은 이 문서 맨 끝 '남은 작업'에 있다.

> 무엇을 먼저 만들 것인가. 설계 문서는 **무엇을 만들지**를 정하고 이 문서는 **어떤 순서로**를 정한다. 새 규칙을 만들지 않는다.

## 원칙 — 근거 품질을 한 단계씩 올린다

03의 `information_status`는 이미 네 단계다.

```text
timetable_only  공시 시간표만. 관측 없음          ← 04·05만 있으면 된다
observed        유효 관측이 있음                  ← 06 수동 수집이 붙으면
stale           관측이 낡음
unavailable     제공 못 함
```

**`timetable_only`만으로도 앱은 완성품이다.** 학생이 "다음 셔틀 언제"를 묻고 공시 시각을 정확히 받는다. 관측·통계·GPS는 전부 그 위에 얹는 **품질 개선**이지 동작 조건이 아니다.

그래서 순서의 뼈대는 이것이다 — **먼저 쓸모 있는 것을 만들고, 그 다음에 정확하게 만든다.** 예측 엔진을 다 만들고 나서 화면을 만들면 몇 주 동안 볼 게 없고, 04·05가 틀렸다는 것도 끝에 가서야 안다.

`00` 7장의 순서를 이 원칙으로 다시 쪼갠 것이 아래다. 가장 큰 차이는 **학생 화면을 5번에서 2번으로 올린 것**이다.

## P0 — 골격 — **완료**

**목표:** 빈 그릇이 돌아간다.

| 할 일 | 근거 |
|---|---|
| 저장소, Docker Compose (postgres · api · web) | `14` 2장 1단계 |
| 마이그레이션 도구 도입. 앱 인스턴스가 동시에 실행하지 않게 | `14` 10장 |
| 스키마를 **15의 층 순서대로** 생성 | `15` |
| 01의 오류 응답 봉투, 충돌 코드, 인증 뼈대 | `01` |

**스키마를 층 순서대로 만드는 이유.** 15는 아래층이 위층을 참조한다 — ① 기준 → ② 날짜 → ③ 관측 → ④ 계산 → ⑤ 운영. 이 순서로 만들면 FK가 가리키는 테이블이 **항상 이미 있다.** 반대로 가면 순환처럼 보이는 지점에서 막힌다.

**완료 판정:** FR-DM-01 (FK 방향 검사), 마이그레이션 up/down 왕복.

## P1 — 기준 자료 — **완료**

**목표:** 시간표가 DB에 정확히 들어간다.

| 할 일 | 근거 |
|---|---|
| 노선·정거장·패턴 등록. 패턴 분리 표 그대로 | `04` 9장 |
| 공시 시간표 148행 적재 | `04` 5장 A~C |
| `X` 판별 — 기점 이전 / 비고 출발 | `04` 2장 |
| `경유`·범위형·공란을 원문 값으로 보존 | `04` 2장 |
| `service_calendar`, 회차 생성 배치, 예외 | `05` |
| 학생회관 해당 회차 판정 `[13:30, 15:30]` | `04` 7장 |

**왜 최우선인가.** 여기가 틀리면 그 위에 만드는 전부가 틀린 값 위에서 돈다. 예측이 아무리 정교해도 기점을 잘못 잡으면 의미가 없다. 그리고 **이 단계는 지금 당장 자료가 전부 있다** — 노선 경로도, 기기 설치 허가도, 관측 표본도 필요 없다. 막힐 이유가 없는 유일한 단계다.

**완료 판정:** FR-RD-01~12·23, FR-SC 전체. 특히 FR-RD-01의 행 수 합계(42/33/38/7)를 눈으로 맞춰본다.

**이 단계에서 원문을 다시 만난다.** 지금 미확정인 것들 — 펜타포트 좌표, 온양 학생회관 해당 회차 (선문대 = 아산캠퍼스는 2026-09-15 확인) — 이 적재 작업 중에 자연스럽게 결론이 난다. 결론 전에는 `verification_status = needs_interpretation`으로 넣고 지나간다. 멈추지 않는다.

## P3 — 관리자 수동 수집 — **서버 완료 (1·2부), 화면 미착수**

**목표:** `information_status`가 `observed`로 올라간다.

| 할 일 | 근거 |
|---|---|
| 수집 세션 — 시작·종료·점유·인계 | `06` |
| 관측 입력 계약 — 순서·시계·중복·유일성 검사 | `02` |
| 취소, 관리자 검토(승인·기각), **오취소 복구** | `02` 9장, `13` 13·15장 |
| 관리 화면 — 세션 상세, 회차 취소, 공지 | `13` 8장 |

**왜 3순위인가.** 관측이 있어야 뒤의 통계·예측이 입력을 받는다. 그리고 **이 앱이 곧 측정 도구다** (`00` 7장). 스톱워치로 재서 옮겨 적을 필요 없이, 타면서 버튼을 누르면 표본이 바로 쌓인다.

**완료 판정:** FR-MC · FR-OB · FR-OP 전체.

## P6 — GPS 자동화 ← 외부 확인이 선행 조건

**목표:** 사람이 안 타도 돌아간다.

| 선행 조건 | 상태 |
|---|---|
| 기기 설치에 대한 운영 주체의 허가 | **미확보** |
| 노선 경로 조사 (GPX) | **미확보** |

| 할 일 | 근거 |
|---|---|
| 조사 트랙 적재 → `route_path_points`·`route_stop_segments` | `04` 1장, IMPROVEMENTS |
| 단말 인증, 세션 시작·종료 4가지 사유 | `07` 1장 |
| 지오펜스, 선분 판정, 보간 | `07` |
| 경로 이탈 게이트 | `07` 4장 |
| 수동 기록과 GPS 판별 결과 비교 | `00` 3장 Phase 2 |

**미정 설정값이 여기서 실측으로 정해진다** — `dwell_min_seconds`, `terminal_boundary_min_points`, `max_route_deviation_m`, `max_position_accuracy_m`. 그전까지 각 문서의 "결정 전 처리"가 적용된다. P2~P5는 시험값으로 돌려도 되고, 값이 없으면 해당 판정을 하지 않는 쪽으로 이미 설계되어 있다.

**허가부터 확인한다.** 설치가 거절되면 P6 전체가 무산되고 수동 수집이 영구 데이터 소스가 된다. 그 경우 P5의 표본 수집 계획을 다시 짜야 하므로, **P3을 시작할 때쯤 물어보는 게 좋다.** 코드를 다 쓰고 물어보면 늦다.
