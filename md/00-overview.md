# 00 · 개요 — 학교 셔틀 도착 예측 서비스

> 기능별 설계 v7.10. 03·08·11·12의 근거 선택·정렬·발행 규칙과 15 데이터 구조를 반영했다. 변경 내용은 [변경 기록](CHANGELOG.md), 외부 확인 과제는 [개선사항](IMPROVEMENTS.md), 구현 순서는 [로드맵](ROADMAP.md)을 참조한다.
>
> **계약이 아닌 기록** — 계획: [경로 자료](PLAN-route-data.md) · 문헌 검토: [논문 기록](논문.md) · 점검: [REVIEW-2026-09-21](REVIEW-2026-09-21.md)·[REVIEW-2026-09-22](REVIEW-2026-09-22.md) · 근거: [RATIONALE-v7.6](RATIONALE-v7.6.md). 이들은 규칙을 만들지 않으며 위 설계 문서가 계약을 소유한다.
> 이 문서는 설계안이며 구현·운행 검증이 완료되었다는 뜻이 아니다.

## 1. 목적

학교 셔틀의 정거장 도착·통과 시간을 **실제 관측으로 보정**하여 학생의 대기 불확실성을 줄인다.

시간표만으로는 부족하다. 회차마다 정해진 기점에서 출발하는 시각은 시간표와 일치하지만, 출발 이후에는 교통 상황과 정차 시간에 따라 이후 정거장 도착 시각이 달라진다. 그 차이를 실제 통과 기록으로 메운다.

학생은 세 가지를 알 수 있어야 한다.

- 언제 오는 버스인지
- 마지막으로 어디에서 확인되었는지
- 지금 보는 예상 시각이 **무엇에 근거한 값**인지

## 2. 전제

- 회차마다 정해진 기점에서 출발하는 시각은 시간표와 일치한다. 기점은 아산캠퍼스일 수도, 외부 정거장일 수도 있다.
- 정시 출발 전제는 **각 회차의 기점 출발에만** 적용한다. 같은 외부 정거장이라도 다른 회차의 중간 방문이면 도착·통과·재출발을 정시로 가정하지 않는다. 중간 공시 시각, 실제 관측 시각, 예측 시각을 구분한다. 정시 전제로 실제 관측 이벤트를 생성하지 않는다.
- 초기에는 개발자가 직접 동승해 버튼으로 기록한다. 이후 GPS 단말로 자동화한다.
- Docker·Kubernetes는 인프라 학습 목적으로 유지한다. 개인 규모에 과하다는 점을 알고 선택했다.
- **시간표 숫자를 임의로 수정하지 않는다.** 미확정 경로·시각 의미는 확인 필요로 표시한다. 이번 학기 주말 시간표는 확보했으며 이후 미등록 자료는 별도로 구분한다.

## 3. 범위

### MVP — Phase 1

노선 1개, 수동 입력 기반. 실제로 이용하는 노선을 우선한다. **MVP 노선은 천안아산역 노선(아산캠퍼스 ↔ 천안아산역)으로 확정했다** (2026-09-15).

시간표·날짜 자료 상태, 지도·목록 정거장 선택, 수동 관측 기록, 예상 시각, 오류·재연결 처리, 실제 승차 위치 안내.

### Phase 2

GPS 단말로 수집을 자동화한다. 예측 로직과 학생 화면은 유지하고 수집 경로만 바꾼다. 초기에는 수동 기록과 GPS 판별 결과를 비교한다.

### 후속

나머지 3개 노선 실측, 푸시 알림, 오프라인 시간표, 관리자 시간표 편집 화면, 전체 노선 별도 페이지·노선명 검색, 노선 간 통합·환승 검색, 2대 차량의 상세 비교 UI. **MVP에서도 차량 슬롯과 후보 행은 분리한다.** 한 대만 관측해도 다른 예정 슬롯을 숨기거나 합치지 않는다.

**학생회관 승차 위치 안내는 후속으로 미루지 않는다.** MVP에 포함한다.

### 왜 이렇게 나눴나

이전 구조는 레이어(화면/서버/요구사항/함수명)로 나뉘어 있었다. 그러면 **기능 하나가 항상 여러 문서에 흩어진다.** 후보 조회 하나를 구현하려면 다섯 문서를 열어야 했다.

기능별로 자르되, 여러 기능이 공유하는 것은 **계약 문서로 명시적으로 분리**했다. 수동 수집(06)과 GPS(07)는 서로를 참조하지 않는다. 둘 다 관측 계약(02)만 본다. 후보 조회(11)와 실시간 전송(12)은 상태 계약(03)을 공유하고 후보 변경 알림의 연결 규칙을 참조한다.

공유 계약은 의도된 의존성이다. **정의 소유자는 하나로 고정하고**, 다른 문서는 참조와 사용 사례를 둔다. 파일 간 참조를 금지하지 않으며 서로 다른 규칙을 중복 정의하는 일을 막는다.

|---|---|---|

Probe·StatefulSet 설정만으로 가용성·백업 목표를 통과했다고 판단하지 않는다. 학습에 쓴 운행과 평가 운행을 분리한다. **도착 데이터를 수집하지 않았다면 통과 시각 오차로 평가하고 도착 정확도라고 발표하지 않는다.**

기능별 요구사항(FR)은 각 기능 문서의 검증 기준 절에 있다.

## 6. 학습 목표

- Docker로 개발 환경을 재현한다.
- Kubernetes의 Deployment, Service, Ingress, ConfigMap, Secret을 적용한다.
- StatefulSet과 PersistentVolume으로 DB 영속성을 실습한다.
- Liveness·Readiness Probe, 롤링 업데이트, 장애 복구를 검증한다.
- CronJob으로 회차 생성과 구간 통계 갱신을 처리한다.
- 서비스 간 이벤트 전달, 중복 처리 방지, 로그와 상태 관찰을 학습한다.

상세는 `14-infrastructure`.

## 7. 구현 순서

단계별 순서와 완료 판정은 [구현 순서](ROADMAP.md)가 소유한다. 큰 줄기만 옮기면 이렇다.

1. Docker 환경, 15의 층 순서로 스키마 — `14`, `15`
2. 시간표·날짜 상태 등록 — `04`, `05`
3. **시간표만으로 도는 학생 화면** — `03`, `10`, `11`, `12`
4. 입력자 앱으로 동승 기록 수집 — `06`, `02`, `13`
5. 실시간 전달 — `12`, `14` 2단계
6. 공시값과 실측 통계 분리, 예측 구현 — `08`, `09`
7. GPS를 수동 기록과 비교한 뒤 자동화 — `07`
8. 화면 완성, 서비스 분리, Kubernetes — `14`

**3번을 예측보다 앞에 둔다.** `information_status = timetable_only`만으로 학생 화면이 완성품이므로(`03`), 예측을 기다릴 이유가 없다. 일찍 써보면 1·2번의 오류가 하루 만에 드러난다.

4단계의 입력자 앱이 곧 측정 도구다. 스톱워치 대신 이 앱으로 재면 데이터가 바로 DB에 들어간다.

## 8. 미확정 항목

운영 자료가 필요한 값은 **임의로 채우지 않는다.** 결정 전 처리 정책을 각 문서에 정의했다.

| 항목 | 결정 전 처리 | 담당 문서 |
|---|---|---|
| `펜타포트` 위치·좌표 | 휴일 천안역 노선에만 등장. 좌표 확인 전 지도 표시 보류 | `04`, `10` |
| 중간 경유지 구간 소요시간 | 해당 구간 ETA 미제공, `missing_baseline` | `09` |
| 각 정거장 GPS 좌표 | 지도 표시 보류, 확인 필요 표시 | `04`, `10` |
| 학생회관 추가/대체 승차 여부 | 단일 좌표로 확정하지 않음 | `10` |
| 단말 시계 오차 허용·지연 입력 보관 기간 | 모순 기록은 `needs_review` 보관 | `02`, `06` |
| 귀교 경유 경로 | 역순 자동 생성 금지 | `04` |
| `경유` 표기 정거장의 실제 정차 여부 | `boarding_policy = unknown` | `04` |
| GPS 반경·전송 간격·세션 종료 시점 | 시험값 사용, 실측 후 확정 | `07` |
| 신선도·관측 만료 시험값 | 시험값 사용, 실측 후 확정 | `11`, `08` |
| 통계 스냅샷 보존 기간 | 이전 버전 보존, 정리 작업 미적용 | `09` |
| 여러 입력자 인계 방식 | MVP는 한 세션 한 입력자, 인계는 관리자 확인 | `06` |
| 이력·예측·원시 GPS 보존 기간 | 정리 작업 미적용 | `00`, `07` |
