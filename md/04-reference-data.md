# 04 · 기준 데이터

> 노선·패턴·정거장·시간표 원본을 다룬다. **적용 기간과 버전으로 관리하는 원본·템플릿**이며, 날짜별 회차 생성은 `05-service-calendar`가 맡는다.
> 참조: [공통 규약](01-conventions.md)
> 출처: 「2026-2학기 셔틀버스 시간표_평일.pdf」, 「2026-2학기 셔틀버스 시간표_휴일.pdf」 각 1페이지. 표·범례·주의사항을 렌더링 이미지로 대조했다.

**공시 시각을 임의로 수정하지 않는다.** 통계와 다르더라도 원문을 보존하고 차이를 기록한다.

## 1. 정거장과 노선 모델

| 테이블 | 주요 열 |
|---|---|
| `stops` | `stop_id`, `name`, `latitude`, `longitude`, `geofence_radius_m`, `verification_status` |
| `routes` | `route_id`, `name`, `short_name`, `is_active` |
| `route_patterns` | `route_pattern_id`, `route_id`, `pattern_code`, `direction`, `verification_status` |
| `route_versions` | `route_version_id`, `route_pattern_id`, `version_no`, `effective_from`, `effective_to`, `note` |
| `route_stops` | `route_stop_id`, `route_version_id`, `stop_id`, `stop_sequence`, `is_origin`, `is_terminal`, `boarding_policy`, `alighting_policy`, `note` |
| `route_path_points` | `route_version_id`, `path_seq`, `latitude`, `longitude`, `path_source`, `recorded_at` |
| `route_stop_segments` | `route_version_id`, `from_route_stop_id`, `to_route_stop_id`, `path_from_seq`, `path_to_seq`, `distance_m`, `path_source`, `verification_status` |

### 실제 주행 경로

`route_stops`는 방문 **순서**만 갖는다. 정거장 사이를 어느 도로로 가는지는 별도 자료이며, 학교 문의로 확보하지 못해 사용자가 직접 확인한다 ([개선사항 1순위](IMPROVEMENTS.md)).

| 테이블 | 무엇 |
|---|---|
| `route_path_points` | 경로 폴리라인. 지도 표시와 경로 이탈 판정에 쓴다 |
| `route_stop_segments` | 두 방문 사이가 폴리라인의 어느 구간인지. `path_from_seq`~`path_to_seq` |

**`route_stop_segments`가 핵심이다.** "좌표가 B 다음 구간에 있다"를 판정하려면 구간의 범위를 알아야 하며, 그것이 GPS 공백 복원(`07` 5장)이 기다리는 자료다. 폴리라인만 있고 구간 분할이 없으면 그 판정을 할 수 없다.

`path_source`는 값의 출처다. `09`의 `baseline_source`와 같은 발상으로, 어디서 온 좌표인지 모르면 신뢰도를 판단할 수 없다.

| 값 | 의미 |
|---|---|
| `recorded_track` | 실제 탑승하며 기록한 트랙 |
| `operator_provided` | 운영 측이 제공한 자료 |
| `manual_trace` | 지도 위에서 손으로 그림 |

`manual_trace`는 도로 중심선 추정이라 실제 주행 차선과 어긋난다. **지도 표시에는 쓰되 `07`의 경로 이탈·공백 복원 판정에는 쓰지 않는다.** `09`의 `estimate`를 공개 예측에서 제외하는 것과 같은 이유다.

`route_version_id`에 붙는 이유는 휴일 천안역처럼 패턴마다 경로가 다르고, 개정 후에도 과거 회차가 자기 버전의 경로로 해석되어야 하기 때문이다. 왕복의 가는 길과 오는 길은 같은 `route_version` 안에서 `path_seq` 순서로 이어지며, 별도 방향 열을 두지 않는다 — 한 회차가 곧 한 바퀴이기 때문이다.

확인 전에는 두 테이블이 비어 있고, 그동안 지도는 정거장 연결 직선을 '정거장 연결선'으로 표시한다 (`10` 5장).

### 조사 트랙 — 경로 자료의 원본

`route_path_points`는 **정제된 결과**다. 그것을 만들어낸 원본 기록을 따로 보존한다.

| 테이블 | 주요 열 |
|---|---|
| `survey_tracks` | `survey_track_id`, `route_version_id`, `recorded_on`, `device_label`, `gpx_version`, `point_count`, `imported_at`, `note`, `source_file_hash` (unique), `source_file_ref`, `app_version`, `export_format`, `recording_settings` |
| `survey_track_points` | `survey_track_id`, `point_seq`, `measured_at`, `latitude`, `longitude`, `elevation_m`, `speed_mps`, `bearing_deg`, `sat_count`, `hdop`, nullable `accuracy_m`, `raw_extensions` |
| `survey_annotations` | `annotation_id` (PK), `survey_track_id`, `annotation_seq`, `latitude`, `longitude`, nullable `measured_at`, `label`, nullable `linked_point_seq`, nullable `resolved_route_stop_id`, `verification_status` |

원본을 남기는 이유는 넷이다.

- 같은 패턴을 **두 번 이상** 타서 재현되는 구간만 `verified`로 올린다 ([개선사항](IMPROVEMENTS.md)). 두 트랙을 비교하려면 둘 다 있어야 한다.
- 단순화 허용 오차를 바꿔 폴리라인을 다시 만들 수 있다.
- 정거장별 `geofence_radius_m`의 근거가 된다 (`07` 7장).
- 정거장의 실제 승차 좌표를 정하는 근거가 된다.

`survey_track_points`는 운행 중 좌표(`07`의 `device_positions`)와 **다른 테이블이다.** 조사 트랙은 회차에 배정되지 않으며 생산자 세션에도 속하지 않는다. 승객으로 탑승해 기록한 자료이므로 관측(`02`)을 만들지 않는다.

`survey_annotations`는 독립된 지점 표시다. UNIQUE(survey_track_id, annotation_seq)로 원문 순서를 구분하고 주석 자체의 좌표·시각을 보존한다. 원문에 시각이 없으면 null이다. linked_point_seq는 같은 트랙의 point_seq를 참조하는 선택 연결이며 주석 원본을 덮지 않는다. 경로 점이 0개인 주석 전용 파일도 허용한다. `label`은 적어 넣은 원문이고 `resolved_route_stop_id`는 매핑 결과이며, 확인 전에는 null이다. 13장의 `source_stop_labels`와 같은 방식으로 원문과 확정 지점을 분리한다.

**정거장 좌표는 표시 지점 자체가 아니라 그 부근 정차 구간에서 정한다.** 버튼을 누르는 시점이 실제 정차보다 늦기 때문이다. `speed_mps`가 0에 가까운 연속 구간을 후보로 삼고 현장 주석·방문 순서와 대조한 후 대표값을 쓴다. 신호대기를 정거장 정차로 단정하지 않는다. 정차하지 않은 방문이나 주석 전용 파일은 정차 구간을 만들지 않고 별도 현장 확인 전까지 확인 필요로 남긴다.

`accuracy_m`은 nullable이다. 표준 GPX에는 해당 필드가 없고 `sat`·`hdop`·`fix`만 있으므로, 기록 앱이 확장 요소로 넣은 경우에만 채워진다. 값이 없어도 `raw_extensions`에 원문을 보존해 나중에 다시 해석할 수 있게 한다.

### 패턴과 버전은 다른 축이다

- **패턴**은 같은 날 공존할 수 있는 서로 다른 경로다. 천안역 노선의 일반 왕복과 중간노선 전용은 같은 날 둘 다 운행한다.
- **버전**은 한 패턴의 개정판이다. 시간이 지나며 교체된다.

같은 날 공존하는 패턴을 시간 순서의 개정 버전으로 취급하지 않는다.

### 같은 노선이 요일별로 다른 패턴을 갖는다

천안역 노선이 실제 사례다. 평일과 휴일의 방문 목록이 다르므로 **별도 패턴**으로 등록한다.

```
평일  캠퍼스 → 월봉청솔1단지 → 쌍용동하이마트 → 천안역
      → 하이렉스파건너편 → 용암마을 → 캠퍼스                     (7 방문)

휴일  캠퍼스 → 펜타포트 → 천안아산역 → 월봉청솔1단지 → 쌍용동하이마트
      → 천안역 → 하이렉스파건너편 → 용암마을 → 천안아산역 → 캠퍼스  (10 방문)
```

**휴일 패턴에서 천안아산역이 두 번 등장한다.** 3번째 방문(가는 길)과 9번째 방문(오는 길)은 같은 `stop_id`이지만 다른 `route_stop_id`다. 이 구분이 무너지면 후보 조회와 통과 판별이 전부 깨진다.

이로 인해 **휴일에는 천안아산역에서 두 노선을 탈 수 있다.** 선택 노선 안에서는 반복 방문을 구분한다 (`11`). 다른 노선의 후보를 한 목록에 합치는 기능은 후순위다.

### 순서는 `stops`에 두지 않는다

같은 정거장이 여러 노선에, 한 회차 안에서도 반복 등장한다. 순서는 `route_stops.stop_sequence`가 갖는다. 노선 변경 후에도 과거 기록을 해석할 수 있도록 운행에 적용된 `route_version_id`를 보존한다.

### 승차와 하차를 분리한다

`boarding_policy`와 `alighting_policy`를 각각 둔다. 값은 `allowed` / `not_allowed` / `unknown`.

- 기점: 승차 허용, 하차 불가
- 캠퍼스 종점: 하차 허용, 승차 불가
- 주요 외부 정거장(시간표 열에 시각이 공시된 천안아산역·천안역·천안터미널·주은아파트 버스정류장·온양온천역·아산터미널): 중간 방문이면 승차·하차 모두 허용 (2026-09-15 사용자 확인). 휴일 천안역 패턴의 천안아산역 두 방문도 포함한다
- 그 밖에 경유지 중 확인되지 않은 곳: 양쪽 `unknown`

**`unknown`을 '탑승 가능'으로 표시하지 않는다.** 공식 안내가 중간 승차지에서 손을 들어 의사를 표시하라고 요구하므로 모든 경유지의 정차가 보장되지 않는다.

## 2. 원문 표기 보존

`X`, 공란, `경유`, 시각, 비고 출발을 **서로 다른 원문 값으로 보존한다.** 파서가 빈 칸에 새 시각을 만들어 채우지 않는다.

보존 위치는 `trip_templates.source_cells`(JSONB)다. 열마다 원문 값과 판별 결과(`time` / `via` / `before_origin` / `not_visited` / `unresolved`)를, 행마다 금요일 표기와 비고를 담는다. `X`는 시각이 없으므로 `scheduled_stop_times`에 행이 생기지 않고(FR-RD-07) 이 열에만 남는다.

### `X`의 세 가지 의미

| 의미 | 판별 근거 | 예 |
|---|---|---|
| **기점 이전** | **앞쪽 칸에 시각이 없고 뒤쪽 칸에 있다.** 그 회차가 해당 지점보다 뒤에서 출발한다 | 평일 천안아산역 순2의 캠퍼스 출발, 평일 온양 순2의 주은아파트 |
| **미방문** | **앞쪽과 뒤쪽 칸에 모두 시각이 있다.** 운행 도중 그 정거장만 건너뛴다 | **원문에 사례 없음** |
| **비고 출발** | 주요 열이 모두 X이고 실제 기점이 비고 칸에 있다 | 평일 천안역 순5, 터미널 순9 |

판별 근거는 **X 앞뒤에 시각이 있는가 하나뿐이다.** 같은 행에 X가 여러 개 연속해도 첫 시각 앞이면 전부 기점 이전이다.

**전체 회차표를 훑은 결과 `미방문`에 해당하는 X는 하나도 없다.** 모든 X는 그 행의 첫 시각보다 앞에 있다. 따라서 지금은 기점 이전과 비고 출발 둘만 구현하면 되고, `scheduled_trip_stops`에 방문을 만들지 않는다는 처리도 같다 (`05` 4장).

미방문이 나중에 확인되면 **별도 패턴으로 등록한다.** 방문 목록 자체가 다르기 때문이며, 기존 패턴에 건너뛰기 표시를 더하지 않는다 (9장). 그 전까지 `route_stops`에 미방문 표기 열을 만들지 않는다.

판별이 끝나지 않은 `X`는 `verification_status`를 확인 필요로 두고 **기점 추정에 사용하지 않는다.**

### `경유`

방문은 예정되어 있으나 예정 시각이 공시되지 않았다는 뜻이다. 승차 허용 여부는 별개이며 확인 전에는 `boarding_policy = unknown`이다.

### 범위형 소요 안내

평일 표의 일부 중간 정거장 칸에 `5~10분`, `5~20분` 같은 범위 안내가 있다. **"중간 정보가 전혀 없다"고 단정하지 않는다.**

```
schedule_annotations(
  annotation_id, source_page, route_id, trip_no,
  covered_stop_ids, raw_text, min_seconds, max_seconds,
  reference_stop_id, verification_status
)
```

기산점이 명확하지 않으면 `reference_stop_id = null`, `verification_status = needs_interpretation`으로 두고 **정밀 구간 ETA에 사용하지 않는다.** 임의의 평균값으로 바꾸지 않는다.

## 3. 시간표 모델

| 테이블 | 주요 열 |
|---|---|
| `schedule_templates` | `schedule_template_id`, `name`, `day_type`, `effective_from`, `effective_to`, `data_status`, `source_reference`, `verified_at` |
| `trip_templates` | `trip_template_id`, `schedule_template_id`, `route_version_id`, `trip_no`, `source_row_key`, `origin_route_stop_id`, `excluded_weekdays`, `vehicle_count_by_weekday`, `schedule_source`, `punctuality_assumption`, `source_cells`, `note` |
| `scheduled_stop_times` | 키 `(trip_template_id, route_stop_id, event_type)`; 공시 시각, `event_type`, `day_offset`, `raw_value` |

### `day_type`

`weekday` / `saturday` / `sunday_holiday`

### 운행기간이 템플릿마다 다르다

| 템플릿 | `effective_from` | `effective_to` |
|---|---|---|
| 평일 | 2026-09-01 (화) | 2026-12-14 (월) |
| 토요일 | 2026-09-05 (토) | 2026-12-13 (일) |
| 일요일·공휴일 | 2026-09-05 (토) | 2026-12-13 (일) |

학기 안의 모든 주말이 휴일 기간에 포함되는지 확인했다. 첫 주말 9/5·9/6, 마지막 주말 12/12·12/13 모두 범위 안이다.

### `scheduled_stop_times`

키에 `event_type`이 들어가므로 같은 방문의 도착·출발을 각각 저장할 수 있다.

| `event_type` | 언제 |
|---|---|
| `arrival` | 그 시각이 도착임이 확인됨 |
| `departure` | 그 시각이 출발임이 확인됨 |
| `unspecified` | 시각은 있으나 도착·출발 구분이 확인되지 않음 |

**한 시각을 도착·출발 양쪽에 복제하지 않는다.** 두 시각을 각각 확인한 경우에만 두 행을 둔다. `unspecified`의 의미가 확인되면 확정된 한 종류로 정정한다.

2026-2학기 원문은 모두 의미가 확인되어 `unspecified` 행이 없다 (5장 열의 의미). 새 원문을 받으면 열의 의미를 다시 확인한다.

`origin_departure_time`과 `terminal_arrival_time`만 저장하면 왕복 회차의 외부 정거장 출발 시각과 온양 노선의 중간 시각이 사라진다. **주요 지점의 모든 공시 시각을 `scheduled_stop_times`에 보존한다.**

### 출처·정시성·실측의 분리

세 가지는 서로 다른 축이다. 하나로 합치지 않는다.

| 위치 | 값 | 의미 |
|---|---|---|
| `scheduled_stop_times.schedule_source` | `school_pdf` / `operator_entry` / `unknown` | 공시 시각의 **출처** |
| `trip_templates.punctuality_assumption` | `user_asserted_on_time` / `not_assumed` | 정시성 **운영 전제** |
| `trip_vehicles.departure_observation_event_id` | 이벤트 ID 또는 null | 실제 출발 **관측** |

기점이 학교인지 외부 정거장인지와 무관하게 **검증된 각 회차의 기점 출발**에 `punctuality_assumption = user_asserted_on_time`을 적용한다. 공식 PDF에서 읽은 공시값의 `schedule_source`는 `school_pdf`이다. 같은 물리적 정거장이라도 다른 회차의 중간 방문이면 정시 출발 전제를 적용하지 않는다. **공식 출처와 정시 보장은 다르다.** PDF는 교통·공사·기상에 따른 지연 가능성을 안내한다.

PDF 본문·비고에서 읽은 값은 출처가 `school_pdf`이다. 의미 해석이 불확실한 경우 출처를 unknown으로 바꾸지 말고 `verification_status`를 미확정으로 둔다. 기점 또는 출발 시각을 확정하지 못한 회차는 정시 전제로 빈 시각을 채우지 않는다. 실제 관측은 차량·회차에 저장하며 템플릿 전체를 observed로 바꾸지 않는다.

### `source_row_key`

`(시간표 버전, 노선, 원본 순)`으로 원본 행을 식별한다. 요일별 복사표는 같은 원본 행에 적용되는 운행 조건으로 합친다. **금요일 표를 별도 평일 템플릿으로 중복 등록하지 않는다.**

## 8. 공휴일 예외

주말과 통합하지 않고 **독립 규칙**으로 관리한다. 운행 없음은 주말 시간표와 무관한 별개 상태다.

| 날짜 | 요일 | 처리 | `exception_type` |
|---|---|---|---|
| 2026-09-24 ~ 09-26 | 목~토 | 추석연휴, 운행 없음 | `no_service` |
| 2026-10-03 ~ 10-04 | 토~일 | 개천절연휴, 운행 없음 | `no_service` |
| 2026-10-05 | 월 | 개천절 대체휴일, **일요일 시간표 적용** | `alternate_schedule` |
| 2026-10-09 | 금 | 한글날, 운행 없음 | `no_service` |
| 2026-10-28 | 수 | 개교기념일, 운행 없음 | `no_service` |

- 09-26, 10-03, 10-04는 원래 주말이지만 **명시적으로 운행 없음**이다. 휴일 시간표가 있어도 이 날짜는 `no_service`가 우선한다.
- 10-05는 월요일이지만 일요일 시간표를 적용한다. **실제 날짜의 요일 조건이 아니라 참조한 `day_type = sunday_holiday`의 규칙으로 평가한다.**
- 두 PDF의 공휴일 안내가 일치한다.

판정 절차는 `05-service-calendar`가 소유한다.

## 9. 시드 매핑

### `schedule_templates`

| `name` | `day_type` | `effective_from` | `effective_to` | `data_status` |
|---|---|---|---|---|
| 2026-2학기 평일 | `weekday` | 2026-09-01 | 2026-12-14 | `available` |
| 2026-2학기 토요일 | `saturday` | 2026-09-05 | 2026-12-13 | `available` |
| 2026-2학기 일요일·공휴일 | `sunday_holiday` | 2026-09-05 | 2026-12-13 | `available` |

**세 템플릿 모두 자료 확보 완료.** 이전 버전에서 `missing`이던 주말 두 개가 해소됐다.

### `trip_templates` 채우는 법

| 열 | 값 |
|---|---|
| `trip_no` | 표의 `순` 번호 |
| `route_version_id` | 그 요일에 적용되는 패턴의 버전. **천안역은 평일·휴일이 다르다** |
| `origin_route_stop_id` | 검증한 실제 기점. 천안역 순5·터미널 순9는 비고의 외부 출발이 기점이다 |
| `excluded_weekdays` | 평일 템플릿에서 `금(X)`면 `['fri']`, 아니면 `[]`. 휴일 템플릿은 항상 `[]` |
| `vehicle_count_by_weekday` | 평일 예: 순4는 `{"mon":2,"tue":2,"wed":1,"thu":1,"fri":1}`, 순7은 `{"mon":2,"tue":2,"wed":2,"thu":2,"fri":1}` |
| `note` | `중간노선 전용`, `학생회관` 등 |

토요일의 모든 회차는 `{"sat":1}`, 일요일·공휴일의 모든 회차는 `{"sun":1}`을 등록한다. 05에서 결정한 `effective_service_weekday`로 조회한다. 필요한 키가 없거나 대수가 양의 정수가 아니면 자료 오류로 처리하며 0대 또는 임의 기본값으로 생성하지 않는다.

`vehicle_count` 단일 값으로는 "월~화만 2대"를 표현할 수 없다. **JSONB로 요일별 대수를 저장한다.** 대표 1대만 실측하더라도 예정 대수를 메모에만 두면 금요일 표시가 틀린다.

## 13. 원문과 물리 지점의 매핑

`source_stop_labels(source_reference, raw_name, provisional_stop_id, resolved_stop_id, verification_status, note)`로 원문 이름과 확정 물리 지점을 구분한다. 확인 전에는 `resolved_stop_id`를 null로 두고 원문 이름의 잠정 지점을 따로 제공하며 임의 좌표로 합치지 않는다. 확인 후 새 적용 버전에 매핑하고 이미 시작·관측된 회차 ID는 바꾸지 않는다.

**선문대는 2026-09-15 사용자 확인으로 아산캠퍼스에 매핑했다** (`resolved_stop_id` = 아산캠퍼스, `verified`). 운행·관측이 시작되기 전이라 잠정 패턴을 새 버전으로 남기지 않고 천안터미널 일반 패턴 하나로 합쳤다.

시간표 숫자, X·경유·공란, 원본 행 번호는 이번 수정에서 변경하지 않았다. 휴일 온양 미운행은 단순 빈 배열이 아니라 해당 휴일 원본의 전체 노선 범위 확인을 근거로 05의 `confirmed_no_service` 자료 범위에 등록한다. 새 자료가 누락된 경우에는 같은 결론을 추론하지 않는다.
