## 개선사항 1순위 — GPS 수신 복구와 노선 기반 진행 위치 재확인

**우선순위 1순위 · 상태: 해결됨(확보 경로 확정).** 학교 답변으로 공식화된 자료가 없다는 점을 확인했다(사용자 전달). 따라서 **자료를 어떻게 얻을지 더 찾지 않는다.** 사용자가 직접 방문하거나 운영 업체에 문의해 확보하는 것으로 방침을 확정한다. Phase 2 GPS 수집에 관한 사항이다.

| 구분 | 내용 |
|---|---|
| 담당 | 사용자 |
| 확보 방법 | 운영 업체 문의 또는 직접 탑승·현장 확인 |
| 학교 경로 | 문의 완료, 공식 자료 없음으로 종료 |

### 적용 게이트

**방침이 정해진 것과 자료가 등록된 것은 다르다.** 아래는 실제 경로·좌표 자료가 들어온 뒤에 켠다. 자료가 없는 동안의 동작은 이미 각 문서에 정의되어 있으므로 추가 결정이 필요하지 않다.

| 대기 중인 기능 | 소유 문서 |
|---|---|
| 좌표가 다음 구간에 있다는 이유로 지난 방문 자동 확정 | 07 |
| GPS 공백 구간의 누락 방문 재판별 | 07 · 08 |
| `position_status` 자동 복구 판정 세부 규칙 | 03 |
| 복구 좌표를 예측 근거로 자동 생성 | 08 |

보간 허용 간격·복구 판정 임계값·경로 이탈 허용값은 자료 확보 전에 임의로 정하지 않는다. **수동 기록 기반 계산은 이 확인과 독립적으로 적용한다.**

### 해결하려는 문제

GPS 좌표 수신이 잠시 끊긴 사이 버스가 정거장을 통과하면, 다시 좌표가 들어와도 그 방문이 계속 도착 전으로 남을 수 있다. 장애를 학생에게 알리는 데 그치지 않고 누락 구간을 재확인하여 현재 위치·지난 방문·남은 후보를 복원하는 과정이 필요하다.

### 검토할 복구 흐름

1. 마지막 확인 좌표·측정 시각·회차·방문 순서·진행 방향을 보존한다.
2. 수신 중단을 감지하고 자동 재연결 또는 수신 재개를 기다린다. 좌표 전송 중단과 GPS 측정 중단을 구분한다.
3. 단말에 누적 좌표가 있으면 재전송받아 측정 시각 순서로 검증한다.
4. 복구된 연속 좌표를 확인된 실제 주행 경로와 대조해 진행 위치를 다시 판별한다.
5. 정해진 경로를 따라 특정 방문 이후로 진행했다는 근거가 충분할 때 누락 방문을 복원한다. 우회·왕복·반복 방문 때문에 애매하면 추가 좌표를 기다린다.
6. 검증한 현재 위치·방문 상태·예측·탑승 후보를 일관된 상태로 갱신한다.

예: 학교 → A → B → C에서 A 이후 수신이 중단되었다가 B 이후 구간에서 복구되면, B 방문 여부를 다시 확인한다. 현재 좌표가 B와 가깝다는 사실이나 예정 시각 경과만으로 통과를 확정하지 않는다.

통과 여부 복원과 정확한 통과 시각 복원은 별개다. 실제 저장 좌표가 없고 시각 추정 근거도 부족하면 통과 시각을 만들지 않는다. 노선상 진행으로 추론한 기록은 실측과 구분한다.

### 학생 화면 방향

- 내부 오류명이나 ‘서버 끊김’을 그대로 표시하지 않는다. GPS 수신 중단을 서버 장애로 단정하지 않는다.
- 재확인 중에는 **‘위치 확인 중’**을 사용한다. ‘위치 탐색 중’은 대체 문구 후보로 둔다.
- 마지막 위치에는 마지막 확인 시각을 남기고, 관측하지 않은 가상 이동을 만들지 않는다.
- 신뢰할 수 없게 된 ETA를 계속 노출하지 않고 필요한 경우 시간표를 참고 정보로 제공한다.
- 복구·검증 후 정상 위치와 후보로 갱신한다. 별도의 복구 완료 팝업이나 알림은 기본적으로 필요하지 않다.

### 학교에 확인할 사항 (종료 — 공식 자료 없음)

아래는 학교에 물었던 항목이며 **답변으로 공식 자료가 없음을 확인해 이 경로는 닫는다.** 같은 내용을 아래 ‘직접 확인할 사항’과 현장 확인으로 옮긴다. 다시 문의하지 않는다.

| 항목 | 확인 목적 |
|---|---|
| 노선·방향별 실제 주행 경로 | 정거장 연결 직선이 아닌 실제 경로 확보 |
| 공사·정체 등에 따른 우회 가능성과 안내 방식 | B 이후 위치에 있다는 이유만으로 B를 경유했다고 오판하지 않기 |
| 왕복·순환 구간과 같은 정거장의 방향별 승차 위치 | 같은 좌표·이름의 서로 다른 방문 구분 |
| 회차 중 차량·노선 변경 가능성 | 다른 운행의 좌표를 이전 회차에 연결하지 않기 |
| 기존 위치 장치·운행 데이터의 제공 가능 여부 | 사용 가능한 경로·좌표 자료 및 설치 협의 사항 파악 |

### 직접 확인할 사항

| 항목 | 확인 목적 |
|---|---|
| 실제 탑승 경로와 방향별 좌표 | 공식 안내와 실제 주행 비교 |
| 좌표가 끊기는 구간·기간·빈도 | 복구 조건을 실제 환경에 맞게 설계 |
| 통신 중단인지 GPS 측정 실패인지 | 단말 저장·재전송으로 복원 가능한지 구분 |
| 단말의 오프라인 좌표 저장·재전송 지원 | 누락 구간을 실제 기록으로 복구할 수 있는지 확인 |
| 재수신 직후 좌표 오차와 연속성 | 잘못된 위치로 방문 상태를 앞당기지 않기 |
| 노선·방향별 실제 주행 경로와 우회 발생 여부 | 학교 문의로 얻지 못한 항목. 현장 확인으로 대체 |
| 왕복·순환 구간의 방향별 승차 위치 | 같은 좌표·이름의 서로 다른 방문 구분 |
| 회차 중 차량·노선 변경 가능성 | 다른 운행의 좌표를 이전 회차에 연결하지 않기 |

함께 확인하면 좋은 것: `펜타포트` 위치, 학생회관 승차 지점(`04`·`10`의 미확정 항목). 같은 현장 방문에서 닫을 수 있다.

### 확인 후 반영할 문서

- 03: 복구 중·복구 후 학생 표시와 상태 구분.
- 07: 수신 중단 감지, 저장 좌표 재전송, 노선상 재판별 절차.
- 02: 복원 관측과 추론 기록의 신뢰도·중복·지연 처리.
- 08·11·12: 복원 후 예측·후보·화면 갱신 연결.

detection_missed는 공개 방문 상태에서 제외했다. 학생 표시·수동 관측 예측·노선별 승하차 후보 계약은 v7.2에 반영했다. 실제 GPS 공백의 노선 기반 자동 복원만 추가 확인 후 확정한다. 학교 확인 전 보간 허용 간격·복구 판정 임계값·경로 이탈 허용값을 임의로 정하지 않는다.


### 직접 탑승으로 확인할 때

모든 회차를 한 번에 조사하기보다 경로가 다른 패턴·방향을 먼저 확인한다. 평일/휴일 천안역, 중간 기점 전용, 왕복 재방문, 학생회관 승차 시간대처럼 실제 경로 차이가 있는 경우를 구분한다. 같은 이름이어도 승차 위치·도로 방향이 다르면 별도로 기록한다. 날짜·노선·회차·방문 순서·실제 승하차 위치·우회 여부·관측 시각·좌표 공백을 함께 남긴다. 한 번 탑승 결과로 상시 우회 없음이나 모든 회차 동일 경로를 단정하지 않는다. 기록은 승객으로 탑승해 수행한다.

### 기록 방법 — 트랙 녹화

손으로 지도에 그리지 않는다. **탑승하면서 GPS 트랙을 녹화하면 한 번에 네 가지가 나온다.**

| 필요한 것 | 트랙에서 얻는 법 |
|---|---|
| 실제 주행 경로 | 트랙 그 자체 |
| 정거장의 실제 승차 좌표 | 속도가 0에 가까운 정차 구간 |
| `accuracy_m` 실제 분포 | 트랙 포인트의 정확도 필드 |
| 좌표가 끊기는 구간 | 트랙의 시간 공백 |

기록 도구는 **BasicAirData GPS Logger**(안드로이드)를 사용한다. GPX 1.0/1.1·KML·TXT로 내보내며 좌표·고도·속도·시각·위성 수·방향을 점마다 남긴다.

| 설정 | 값 | 이유 |
|---|---|---|
| GPS 업데이트 간격 | 설치 버전의 짧은 지원 간격으로 시험 | 공식 안내의 3초는 상한이며 최소값이 아니다. 실제 간격은 파일에서 확인 |
| 거리 필터 | 10m 안팎 | 간격 필터와 **OR**로 동작한다 |
| 화면 꺼짐 중 기록 | 켬 | 절전으로 중단되면 구간이 통째로 빠진다 |
| EGM96 고도 보정 | 무관 | 고도는 쓰지 않는다 |
| 내보내기 | GPX | 점별 자료가 가장 온전하다 |

**정지·이동 전환 기록은 정차 후보를 찾는 보조 자료다.** 자동 기록이 실제 정차 시각의 정확성을 보장하지 않는다. 측정 간격·속도 오차·수신 공백과 현장 기록을 대조하고 dwell_min_seconds와 정거장 좌표는 반복 실측 후 정한다.

정거장마다 **Annotate(지점 표시)** 로 정거장 이름을 남긴다. 설명까지 붙일 수 있으므로 승차 위치 특징도 함께 적는다. 회차 단위로 파일을 나누고 파일명에 날짜·노선·순번을 남긴다.

**첫 파일을 받으면 `<extensions>`에 정확도 값이 있는지 확인한다.** 표준 GPX에는 그 필드가 없고 `sat`·`hdop`·`fix`만 있다. 없으면 `max_position_accuracy_m`은 조사 트랙으로 정하지 못하며 Phase 2 실제 단말의 보고값으로 정한다 (`07` 7장).

### 등록 절차

```text
1. GPX → survey_tracks · survey_track_points 로 원본 그대로 적재
   Annotate 지점은 survey_annotations 로 분리
2. 이상치 제거 — 되돌아감, 튄 좌표, 정차 중 흔들림
3. 단순화 — 허용 오차 5m 정도로 점 수를 줄인다
4. route_path_points 에 path_seq 순서로 적재
5. survey_annotations 부근의 정차 구간에서 정거장 좌표를 정하고
   resolved_route_stop_id 를 채운다
6. route_stop_segments 에 방문 쌍별 path_from_seq~path_to_seq 와 distance_m 기록
7. path_source = recorded_track, verification_status 설정
```

1단계에서 **원본을 먼저 저장하는 것이 중요하다.** 단순화 오차를 바꿔 다시 만들거나, 두 번째 트랙과 비교하거나, 정거장별 반경을 다시 정할 때 원본이 없으면 다시 타야 한다.

5단계에서 **Annotate 지점의 좌표를 그대로 쓰지 않는다.** 버튼을 누른 시점이 실제 정차보다 늦으므로, 그 부근에서 `speed_mps`가 0에 가까운 연속 구간의 대표값을 정거장 좌표로 삼는다. Annotate는 '어느 정거장인가'를 알려주는 라벨이다.

**정차 구간이 없으면 5단계를 건너뛴다.** 그 정거장을 실제로 서지 않고 지났거나 주석 전용 파일이면 `resolved_route_stop_id`를 null로 두고 `verification_status`를 `needs_interpretation`으로 남긴다. 신호대기를 정차로 단정해 좌표를 만들지 않는다 (`04` 1장). 1단계에서 `source_file_hash`가 같은 파일은 기존 조사 건을 반환하므로 재업로드로 중복 트랙이 생기지 않는다.

3단계 단순화를 생략하면 고빈도 트랙의 점 수가 커질 수 있다. 실제 성능을 측정해 정제본을 조정하고 원본은 유지한다. 5m는 시작값이며 굽은 구간이 뭉개지지 않는지 보고 조정한다.

두 번째 트랙이 들어오면 첫 트랙과 구간별로 대조한다. 두 트랙이 `max_route_deviation_m` 안에서 겹치는 구간만 `verified`로 올리고, 어긋나는 구간은 `needs_interpretation`으로 남긴다. 이 대조가 **`max_route_deviation_m` 자체를 정하는 근거**이기도 하다 (`07` 6·7장).

**한 번 탄 결과를 모든 회차의 경로로 확정하지 않는다.** 같은 패턴을 두 번 이상 타서 재현되는 구간만 `verified`로 올리고, 어긋나는 구간은 `needs_interpretation`으로 남긴다. 우회가 상시인지 일시인지는 한 번으로 알 수 없다.

고정된 정거장 순서와 실제 도로 경로는 구분한다. 시간표의 방문 순서는 출발·도착 후보 검색에 사용할 수 있지만, GPS 공백 사이의 도로 경유를 입증하려면 추가 경로 자료가 필요하다.

### v7.8 공식 안내 정정

GPS 업데이트 간격과 파일 기록 필터는 별개다. 3초를 최소값으로 기술한 이전 설명은 철회한다. 설치 버전에서 지원하는 설정을 확인하고 시험 파일의 실제 시각 간격을 측정한다. Annotate는 다음 위치 측정값을 사용하며 정차 시각을 보장하지 않는다. 근거: [BasicAirData 공식 사용 안내](https://basicairdata.eu/projects/android/android-gps-logger/getting-started-guide-for-gps-logger/).
