## 2. 미검증 좌표 마커·목록 구분

### 수정 방향

1. 기존 `verified` 값을 마커 생성에 사용한다. 확인된 좌표와 확인 필요 좌표를 색뿐 아니라 모양·기호로 구별한다. 구체 색·자산은 화면 담당자가 기존 스타일에 맞춰 선택한다.
2. 미검증 마커의 이름/설명에 '좌표 확인 필요'를 포함한다. 지도에 간단한 범례를 제공하고, 마커의 hover 설명에만 의존하지 않는다.
3. 목록에도 좌표가 있으나 상태가 verified가 아니면 동일한 확인 필요 문구를 표시한다. 좌표 유무는 위도·경도 양쪽을 확인한다. 지도 SDK를 쓰지 못해도 상태가 전달돼야 한다.
4. 좌표 없는 정거장은 목록만 제공하고, 마커 클릭·목록 클릭은 기존 선택 함수를 공유한다. 좌표 확인 상태와 경로 검증 상태를 서로 대신 사용하지 않는다.

### 완료 조건

| 시험 자료 | 기대 결과 |
|---|---|
| 좌표 있음 + verified | 확인된 마커, 불필요한 확인 필요 문구 없음 |
| 좌표 있음 + unverified 또는 needs_interpretation | 구별되는 마커·범례·목록 문구 |
| 위도 또는 경도 없음 | 마커 없음, 목록에서 확인 필요 |
| 동일 stop_id의 반복 방문 | 물리 정거장 마커 하나 유지 |
| 지도 SDK 실패 | 목록 선택과 확인 상태 안내 유지 |

검증에는 별도 화면 시험 자료를 사용한다. 실제 DB에 임시 좌표를 넣거나 verified로 바꿔서 화면 시험을 하지 않는다. 마커 자산 추가 시 외부 이미지 서비스 대신 로컬 자산을 우선한다.

## 3. 경로 요청 취소·늦은 응답 처리

### 수정 방향

1. 노선·날짜 effect에 요청 유효성 플래그 또는 요청 세대 번호를 둔다. cleanup에서 이전 요청을 무효화한 뒤 abort한다.
2. 성공과 실패 **모두** 현재 요청인지 확인한 후 상태를 바꾼다. 취소 오류는 상태·오류 안내를 변경하지 않는다. AbortController만으로 이미 처리 중인 콜백까지 막았다고 가정하지 않는다.
3. 같은 effect의 정거장 조회도 같은 유효성 조건을 적용해 경로와 목록이 다른 선택의 응답으로 섞이지 않게 한다.
4. 새 선택 시 경로·정거장·선택 상태를 비우는 기존 동작은 유지한다. 현재 경로 요청이 실제 실패하면 선만 비우고 정거장 목록 조회는 계속한다.

### 완료 조건

- A 노선 요청을 지연시킨 뒤 B 선택: B 성공 이후 A의 성공·실패·취소를 각각 발생시켜도 B 경로·목록·오류 상태가 바뀌지 않는다.
- 같은 노선에서 날짜를 빠르게 바꿔도 최신 날짜의 결과만 남는다.
- 화면 해제와 React Strict Mode의 effect 재실행에서도 이전 요청이 상태를 변경하지 않는다.
- 최신 경로 요청 실패 시 선은 없고 정거장 목록·카드는 사용할 수 있다. 경로 없음 응답도 선을 만들지 않는다.

지연 순서를 통제할 수 있는 회귀 시험을 추가한다. 단순히 코드를 읽거나 빠르게 클릭한 결과만으로 경쟁 상태가 해결됐다고 판단하지 않는다. 시험 도구는 실제 프론트 프로젝트의 기존 구성을 먼저 사용한다. 참고 구현에는 관련 도구가 없으므로 도입 시 최소 범위와 실행 명령을 기록한다.

### 수정 순서

1. 작업 시작 시 audit와 대상 패키지의 peerDependencies를 다시 확인한다. 확인한 Next 16 패치 버전을 명시적으로 선택해 package.json과 lock을 함께 갱신한다. React·React DOM은 서로 맞추고 타입 패키지도 호환성을 확인한다. `npm audit fix --force`로 변경 범위를 자동 확대하지 않는다.
2. [공식 Next 16 전환 안내](https://nextjs.org/docs/app/guides/upgrading/version-16)를 따라 Node 20.9 이상·TypeScript 5.1 이상을 확인한다. 현재 Docker의 Node 22와 잠금 파일 TypeScript 5.9.3은 최소 조건을 만족하는 구성이지만 실제 이미지 빌드는 별도 확인한다.
3. 현재 `lint: next lint`는 Next 16에서 쓸 수 없으므로 ESLint CLI와 호환되는 Next 설정으로 바꾼다. 현재 package.json에는 ESLint 의존성이 없어 설정 파일과 의존성도 필요하다. build가 lint를 대신한다고 가정하지 않는다.
4. Next 16의 기본 Turbopack으로 개발·프로덕션 빌드를 확인한다. 현재 next.config에는 별도 webpack 설정이 없다. 비동기 요청 API 등 변경 사항은 실제 사용처를 검색해 필요한 부분만 수정한다.
5. `output: standalone`과 Docker의 정적 파일·public 복사 구성이 새 버전에서도 동작하는지 확인한다. Next 공개 환경값은 빌드에 공급하고 실제 키를 로그·계획서에 출력하지 않는다. 로컬 `.env.local` 성공이 Compose 빌드 키 공급까지 증명하지는 않는다.

| 브라우저 데모 서버 | 8000 포트를 잡고 `demo A`·`demo B`를 주던 임시 Node 서버를 종료하고 실제 API(`uvicorn app.main:asgi`)로 바꿨다. 실제 노선 4개와 `Access-Control-Allow-Origin: http://localhost:3000`을 확인했다 |
| 남은 것 | 지도 타일·마커가 눈에 보이는지는 사용자 브라우저에서 `http://localhost:3000` 으로 확인한다. 편의를 위해 카카오 콘솔에 `http://127.0.0.1:3000`도 등록하면 주소를 어느 쪽으로 열어도 된다 |

설치 경고: ESLint 9.39.5의 지원 종료 안내가 있다. 현재 Next 설정이 사용하는 eslint-plugin-react의 peer 범위가 ESLint 9까지이므로 10을 강제 설치하지 않았다. audit 취약점과 별개인 도구 유지보수 후속 항목이다. unrs-resolver 설치 스크립트 승인 안내도 있었으며 별도 허용하지 않은 상태에서 검사·빌드가 통과했다.
